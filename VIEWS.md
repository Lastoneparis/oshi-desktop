# View inventory — OSHI desktop vs OSHI macOS (Catalyst)

**Target of the port:** the macOS app, which is the iOS app built with Mac Catalyst — same `Info.plist`, same linked frameworks, only the entitlements differ (per `PARITY.md`). So this inventory is of the **iOS/SwiftUI surface** in `/Users/HUGOMORICEAU/Documents/Genesis/OSHI/*.swift`. It is the view-level companion to `PARITY.md` (capabilities) and continues from `PLAN.md`/`PLAN_MESH.md` (protocol + mesh, no UI yet — Tier 1.1 in `PARITY.md` is still ⬜).

**How this was built.** `grep -rn "^struct .*: View\b" *.swift` over the 195-file `OSHI/` tree returns **274 SwiftUI `View` structs across 83 files**. Not every struct is a screen — most files bundle a top-level screen with its private row/badge/button/chip subcomponents in the same file. This document lists one row per **independently meaningful unit** — a full screen, a sheet, a `fullScreenCover`, a modal overlay, or a component big enough that a desktop dev would build it as its own piece of work (e.g. `MessageBubble`, the camera-capture sheet, a map panel). Pure micro-components with no independent navigation or state (`ContactRow`, `StatCard`, `FilterChip`, a single `Icon` view) are folded into their parent's row and named there instead of given their own line. See §5 for the exact count and how it was taken.

**Status column.** Every row is ⬜ **not started** — `OSHI-Desktop/` has a protocol layer and a LAN mesh node (`PLAN.md`, `PLAN_MESH.md`) and, per `PARITY.md` Tier 1.1, zero UI. That is not an oversight in this document; it is the actual state of the repo as read for this pass.

**Portability column — three honest buckets, always with a reason:**

| verdict | meaning |
|---|---|
| **portable as-is** | the screen's information architecture and interaction model transfer directly to a desktop window; no phone-only API (camera, touch gesture, GPS) is load-bearing. Still a full rewrite in Compose Multiplatform (per `PLAN.md` §2's recommendation) — "as-is" describes the *design*, not reused code. |
| **needs a desktop equivalent** | the concept is valid on desktop but the underlying mechanism does not exist there and must be swapped for a different one — named per row. |
| **impossible on Windows+Linux** | no rational equivalent exists; the reason is an OS or App Store affordance, not a missing library. |

Every claim below is traceable to a file I actually read (imports, `.shared` singleton call sites, or the struct body). Where I could not verify something from source I say **unverified** rather than guess.

## The minimum viable window

In build order, each blocking the next:

1. **Key storage that survives a restart** (`PARITY.md` 0.5) — not a view, but nothing below can be built without it; every screen in this document that touches identity assumes it.
2. **`IdentitySetupView` equivalent** — create/recover an identity. Blocks everything.
3. **`ContentView`'s locked/unlocked switch + a desktop app shell** (replacing `MainTabView`'s tab bar — see §7 "different design" below) — the window that decides what's on screen.
4. **`MessagesListView` equivalent** (conversation list) — needs `PARITY.md` 0.13 (local message store) and 0.14 (contacts).
5. **`ChatView` equivalent** (send/receive text only, no media/calls yet) — needs 0.9/0.10/0.12 (keys publish+fetch, message send/pull/ack, router). This is the point at which desktop OSHI is a messenger for the first time.
6. **`ContactSelectorView`/`NewMessageView` equivalent** — start a new conversation. Without it the app can only continue conversations seeded some other way (e.g. QR/manual key paste).
7. **`SettingsView` root + `SafetyNumberView`** — trust verification and basic configuration; not blocking, but the first thing a security-conscious user will look for.

Everything past this point (media, groups, calls, mesh UI, map, bots, AI, steganography, watch, wallpapers) builds on top of a working text-only 1:1 messenger and can come in any order after it — media is the next highest-value addition per the file sizes above (`MediaMessageView.swift` at 2,004 lines is the third-largest view file in the app, after `GroupViews.swift` and `ChatView.swift`).

| View | Reason |

## Views that need a genuinely different design, not a port

- **The 5-tab `MainTabView` shell.** A `UITabBarController`-backed bottom/top tab bar is a phone/tablet pattern (and `ChatsTabView.swift`'s own comments describe a real App-Review-flagged collision between it and the segmented control on iPad). Desktop OSHI needs a sidebar or menu-bar structure — the five destinations (Chats, AI, New Message, Map, More) map cleanly to sidebar sections, but "New Message" as a full *tab* only makes sense as a prominent compose button in a phone tab bar; on desktop it should probably be a toolbar action, not a destination.
- **Everything built around press-and-hold or swipe.** `MessageBubble`'s swipe-to-reply, `ProfessionalAudioInputView`'s press-and-hold-to-record, `MediaMessageView`'s pinch-to-zoom, `WhatsAppMediaCaptureSheet`'s swipe-between-camera-modes. Desktop equivalents: hover-reveal icons or right-click for bubble actions, click-to-start/click-to-stop for recording, scroll-wheel or +/- for zoom, explicit mode buttons for camera capture.
- **`WhatsAppMediaCaptureSheet` (in-app camera capture).** Built for a phone's rear/front camera with a shutter button and mode-swipe. A desktop webcam capture is legitimate but is a secondary path — the primary desktop media flow is "attach an existing file" (`DocumentPicker.swift`'s pattern, which already matches desktop conventions), not "shoot one now."
- **`MediaPickerView`/`ChatWallpaperManager`'s `PhotosUI` pickers.** Swap for a native OS file-open dialog; the surrounding preview/selection UI is otherwise portable.
- **`QRScannerView`/`WebQRScannerView`/`QRScannerImportView` (camera-based QR scanning).** No guaranteed webcam on a desktop machine. Needs a fallback path — upload a QR image, or paste the encoded text/key directly — as the primary path, with live webcam scanning as a bonus if a camera is present.
- **`FirstTimeGuideView`'s spotlight-cutout tutorial.** Anchored to tab-bar icon positions that won't exist in a desktop shell; the tutorial concept survives, the anchoring does not.
- **`DynamicIslandNotificationView`.** Already established above as pure SwiftUI, not real hardware integration — but its "morph from the island" animation has nothing to morph from on desktop. Becomes a standard corner toast.
- **Location- and GPS-dependent screens** (`LocationSharingView`, `CheckInView`, `MapNavigationView`, `GroupFullMapPanel`'s live-tracking mode). A desktop machine is frequently stationary and frequently has no GPS hardware at all; these need either a manual-location-entry fallback or an honest "unavailable on this device" state, not a straight port of "your live position."

## Hidden dependencies

Things a view needs that are not obvious from the view file itself:

- **Biometric unlock (`BiometricLockView`, `SettingsView`'s security section)** needs `LAContext`/Face ID/Touch ID on iOS; on desktop this is a *background mode*-adjacent decision about whether the app can even be trusted to hold decrypted keys in memory while locked — tied to `PARITY.md` 0.5 (key storage), not just UI.
- **`ContentView`'s "unlocking…" branch** depends on iOS's Data Protection class (`keysLockedByDevice`, tripped by `protectedDataDidBecomeAvailable`) — a concept with no desktop OS equivalent; desktop key storage needs its own "are secrets currently accessible" signal (e.g., is the OS keychain/session unlocked).
- **`IncomingCallOverlayView`** depends on `VoIPPushManager`, which depends on PushKit's `PKPushRegistry` to wake the app from a killed state — see "cannot exist" above. Even the *in-app* rendering path implicitly assumes `CXProvider`/CallKit set up the audio session; a desktop version needs its own audio-session lifecycle, not obviously visible from `IncomingCallOverlay.swift` alone.
- **`NotificationManager`-driven banners in `ContentView.swift`** (the "notifications denied" banner) assume `UNUserNotificationCenter` authorization semantics (`.denied` is permanent until the user goes to Settings). Desktop notification permission models differ per OS and need their own re-prompt strategy.
- **`PeersView`/mesh-related screens** need a *running mesh node* in the background at all times, not just on-screen — `PLAN_MESH.md` §6 flags that key storage (identity) is currently generated per-run, in memory, for the desktop mesh prototype; a real client needs that solved before `PeersView`'s desktop equivalent can show a stable identity.
- **`MessagesListView`'s mesh-connected badge and `DynamicMeshBackground`** silently depend on `MeshNetworkManager` being alive and current — a network-reachability signal that has to be wired independent of the view.
- **Every "block/report" screen (`BlockContactSheet`, `ContactActionsView`'s `ReportSheet`)** writes through `BlockedContactsManager`/`ReportManager`, which are presumably backed by local persistent storage (unverified in this pass) that must exist before these sheets mean anything.
- **`QRCodeDisplayView`/`QRScannerView`** encode/decode the identity's public key material — correctness here is a `PARITY.md` §4 concern (base64 vs. base64url, per `PLAN.md` §4.1) more than a UI concern; getting the *view* right without getting the encoding right produces a QR code that silently fails to pair.
- **`ScheduledCallView`'s calendar export** needs calendar read/write permission (`EventKit`) on iOS; a desktop `.ics` export sidesteps needing OS calendar permission at all, which is worth choosing deliberately rather than chasing a permission model that doesn't need chasing.
- **`SettingsView`'s appearance/theme section** reads `@AppStorage("appTheme")` — trivial to port, but note it currently only recognizes `"light"`/`"dark"`/`"system"`; desktop OS theme-change *notifications* (vs. iOS's `colorScheme` environment value) are a different subscription mechanism.
- **Local network permission** (`LocalNetworkPermissionTrigger.swift`, triggered from `PermissionHelper.swift`) gates the mesh's Bonjour/mDNS discovery on iOS 14+. Desktop mDNS (per `PLAN_MESH.md`) needs no such per-app permission dialog on any of the three target OSes today, which is a genuine simplification, not a gap.
